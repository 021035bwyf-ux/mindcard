# 마음카드 — 완전 처음부터 만드는 방법 (자세한 버전)

이 문서는 "마음카드"(청소년 자가진단 + 타로 웹앱)를 **웹 개발을 전혀 모르는 사람**이 처음부터 만든다고 했을 때, 어떤 용어를 알아야 하고 어떤 순서로 무엇을 만들어야 하는지 하나씩 설명합니다. 어려운 용어가 나올 때마다 바로 옆에서 설명을 붙였습니다.

> 더 짧고 쉬운 버전이 필요하면 [HOW_TO_BUILD.md](HOW_TO_BUILD.md)를 먼저 읽어보세요. 이 문서는 그 내용을 훨씬 자세하게 풀어쓴 버전입니다.

## 0. 먼저 알아야 할 기본 용어 (여기부터 읽으세요)

### 웹사이트를 이루는 3가지 재료

웹페이지 하나는 항상 이 3가지 파일의 조합으로 만들어집니다.

| 용어 | 확장자 | 역할 | 비유 |
|---|---|---|---|
| **HTML** (HyperText Markup Language) | `.html` | 화면에 뭐가 있는지(제목, 글자, 버튼, 이미지)를 적는 "뼈대" | 집의 뼈대(기둥, 벽) |
| **CSS** (Cascading Style Sheets) | `.css` | 그 뼈대를 어떻게 꾸밀지(색깔, 크기, 위치, 둥근 모서리) | 벽지, 가구 배치, 인테리어 |
| **JavaScript(JS)** | `.js` | 버튼을 눌렀을 때 실제로 뭔가 동작하게 만드는 "움직임" | 전기 배선, 스위치, 자동문 |

예를 들어 "결과 보기 버튼"이 있다면:
- HTML: `<button>결과 보기</button>` ← 버튼이 화면에 존재하게 함
- CSS: `background: pink; border-radius: 10px;` ← 버튼을 분홍색+둥근 모양으로 꾸밈
- JS: `버튼.addEventListener('click', () => { 결과화면보여주기() })` ← 버튼을 누르면 실제로 결과 화면으로 바뀌게 함

이 3개는 항상 **분리해서** 만듭니다. 뼈대(HTML)는 그대로 두고 꾸밈(CSS)이나 동작(JS)만 따로 바꿀 수 있게 하기 위해서입니다.

### 이 프로젝트에서 자주 나오는 용어들

- **프레임워크(framework)**: React, Vue 같은 "미리 만들어진 큰 도구 세트". 이 프로젝트는 프레임워크를 **쓰지 않고** HTML/CSS/JS만으로 만들었습니다. 이유: 배우기 쉽고, 설치나 빌드(코드를 변환하는 과정) 없이 파일만 열면 바로 동작하기 때문입니다.
- **함수(function)**: "이름 붙인 작업 묶음". 예: `계산하기()`라는 함수를 만들어두면, 그 이름만 부르면 안에 적힌 작업이 실행됩니다. 같은 작업을 여러 번 반복해야 할 때 복사-붙여넣기 대신 함수 하나로 재사용합니다.
- **변수(variable)**: "값을 담아두는 상자". 예: `let step = 0;` 은 `step`이라는 이름의 상자에 숫자 0을 넣어둔 것. 나중에 `step = 1`로 바꾸면 상자 안 내용물이 바뀝니다.
- **객체(object)**: "여러 값을 이름표를 붙여서 하나로 묶은 것". 예: `{ 이름: '외로움 검사', 문항수: 10 }` 처럼 관련된 정보를 하나로 묶어둔 덩어리.
- **배열(array)**: "값을 순서대로 나열한 목록". 예: `['가끔 그렇다', '자주 그렇다', '항상 그렇다']` 처럼 여러 개를 순서 있게 담은 목록.
- **DOM(Document Object Model)**: 브라우저가 HTML을 읽어서 "지금 화면에 뭐가 있는지"를 컴퓨터가 다룰 수 있는 형태로 만들어둔 것. JS는 이 DOM을 조작해서 "버튼을 추가한다", "글자를 바꾼다" 같은 걸 실제로 화면에 반영합니다.
- **이벤트(event)**: "클릭했다", "페이지를 열었다" 같은 사용자의 행동. `addEventListener('click', ...)`은 "클릭이라는 이벤트가 발생하면 ...를 실행해줘"라는 뜻입니다.
- **API(Application Programming Interface)**: 서로 다른 프로그램끼리 데이터를 주고받기 위한 "약속된 창구". 예: 우리 웹사이트가 Supabase(데이터 저장 서비스)에 "이 정보 저장해줘"라고 요청을 보내는 통로가 API입니다.
- **JSON(JavaScript Object Notation)**: 데이터를 텍스트로 주고받기 위한 공통 형식. `{"이름": "외로움 검사", "점수": 17}` 같은 모양. API로 데이터를 주고받을 때 거의 항상 이 형식을 씁니다.
- **서버(server) / 클라이언트(client)**: 서버는 데이터를 보관하고 응답해주는 컴퓨터, 클라이언트는 사용자가 보는 브라우저(웹페이지)를 말합니다. 이 프로젝트는 **자체 서버를 만들지 않고**, 정적 파일(HTML/CSS/JS)만 배포하고, 데이터 저장이 필요한 부분만 Supabase라는 외부 서버 서비스를 빌려 씁니다.
- **정적 사이트(static site)**: 서버에서 매번 계산해서 페이지를 만들어주는 게 아니라, 미리 만들어진 HTML/CSS/JS 파일을 그대로 보여주는 방식의 웹사이트. 만들기 쉽고 무료로 호스팅(=인터넷에 올려서 누구나 접속 가능하게 하는 것)하기 좋습니다.
- **repo / 저장소(repository)**: 프로젝트의 모든 파일과 그 변경 이력을 보관하는 "폴더 + 변경 기록 보관함". Git이라는 도구로 관리합니다.
- **Git / GitHub**: Git은 "파일이 시간에 따라 어떻게 바뀌었는지 기록하는 도구"(버전 관리), GitHub은 그 기록을 인터넷에 올려서 다른 사람과 공유/협업할 수 있게 해주는 사이트입니다.
- **커밋(commit)**: "지금까지 바뀐 내용을 하나의 저장 지점으로 남기는 것". 게임의 저장(세이브) 포인트와 비슷합니다.
- **push / pull**: `push`는 내 컴퓨터의 변경사항을 GitHub(인터넷)에 올리는 것, `pull`은 반대로 GitHub에 있는 최신 내용을 내 컴퓨터로 받아오는 것입니다.
- **배포(deploy)**: 만든 결과물을 실제로 누구나 접속할 수 있게 인터넷에 올리는 작업.

이 용어들만 이해하면 아래 본문을 읽을 수 있습니다.

## 1. 무엇을 만드는가

**마음카드**는 청소년이 부담 없이 해볼 수 있는 간단한 자가진단 웹앱 모음입니다.

- 외로움 / 마음날씨(우울) / 스트레스 / 연애스타일 — 총 4개의 "심리 체크 검사"
- 타로카드 — 카드 3장을 뽑아 운세처럼 메시지를 보여주는 별도 코너
- 각 검사는: 소개 화면 → 문항에 답하기 → 결과 보여주기 → **상담센터 연결 안내(전화/카카오톡)** 순서로 진행됩니다.
- 진짜 목적은 "정확한 진단"이 아니라, 심리적으로 가볍게 접근할 수 있는 콘텐츠를 통해 **실제 상담센터로 자연스럽게 연결하는 것**입니다. 이 목적이 전체 설계(말투, 결과 화면 맨 아래 상담 안내 배치, 공유 기능 등)를 관통합니다.

## 2. 기술 스택 (무엇으로 만들었나)

| 영역 | 선택한 것 | 쉬운 설명 |
|---|---|---|
| 화면(프론트엔드) | HTML + CSS + JS (프레임워크 없음) | 위에서 설명한 "웹사이트를 이루는 3가지 재료"만 사용. 별도 프로그램 설치 없이 메모장으로도 만들 수 있는 수준 |
| 배포(호스팅) | **GitHub Pages** | GitHub에 파일을 올려두면, GitHub이 무료로 `https://아이디.github.io/저장소이름/` 라는 주소로 인터넷에 공개해주는 서비스 |
| 데이터 저장(통계) | **Supabase** | "직접 서버를 만들지 않고도 데이터베이스(정보를 저장하는 곳)를 빌려 쓸 수 있는 서비스". 우리는 "누가 언제 어떤 검사를 봤는지" 같은 기록만 여기 저장 |
| 결과 이미지 생성 | **Canvas API** | 브라우저 안에서 그림을 직접 그릴 수 있게 해주는 JS 기능. 이걸로 서버 없이 "결과 카드 이미지"를 즉석에서 만들어서 공유 가능하게 함 |
| 공유 기능 | **Web Share API** | 스마트폰에서 "공유하기" 버튼을 누르면 뜨는 그 공유창을, 웹사이트에서도 직접 띄울 수 있게 해주는 브라우저 기능 |

**왜 이렇게 "최소한의 도구"로만 만들었나?**
- 빌드(코드를 변환/압축하는 과정) 없이 파일 수정 → 바로 반영이 가능해서, 코딩을 잘 모르는 사람도 유지보수하기 쉽습니다.
- 서버를 직접 운영할 필요가 없어서 비용이 안 듭니다 (GitHub Pages, Supabase 모두 무료 범위 안에서 사용).

## 3. 폴더 구조 — 파일들이 어떻게 정리되어 있나

```
마음체크/
├── index.html              # 첫 화면(허브) — 검사 목록이 카드 형태로 보이는 페이지
├── css/hub.css              # 전체 공통 디자인(색상, 글씨, 버튼 모양 등)
├── js/
│   ├── hub-core.js          # 모든 페이지가 공통으로 쓰는 기능 모음
│   └── test-engine.js       # "검사 진행 화면"을 만들어주는 공용 부품(엔진)
├── tests/
│   ├── loneliness.html      # 외로움 검사 — 문항 내용과 점수 기준만 적어놓은 파일
│   ├── mood.html            # 마음날씨 검사
│   ├── stress.html          # 스트레스 검사
│   └── love.html            # 연애스타일 검사
├── tarot/                   # 타로카드 코너 (검사들과는 별개로 독립적으로 동작)
│   ├── index.html
│   ├── css/style.css
│   └── js/{main.js, tarot-data.js}
├── images/                  # 검사 소개 화면에 쓰이는 그림 파일들
├── stats.html                # 운영자가 보는 통계 화면
└── supabase_setup.sql        # Supabase에 저장 공간(테이블)을 만들기 위한 설정 코드
```

**폴더 구조에서 알아야 할 것**: 파일과 폴더를 기능별로 나눠두면, "검사 4개에 공통으로 적용되는 기능"을 고칠 때 `test-engine.js` 한 파일만 고치면 되고, "외로움 검사만의 문항 내용"을 고칠 때는 `loneliness.html`만 고치면 되게 됩니다. 이렇게 **역할을 나눠서 파일을 분리하는 것**이 유지보수를 쉽게 만드는 핵심입니다.

## 4. 이 프로젝트의 핵심 아이디어: "공용 엔진 + 설정값"

4개의 검사는 문항 내용과 점수 기준만 다르고, **화면이 진행되는 방식(순서, 애니메이션, 공유 버튼, 상담 안내)은 완전히 동일**합니다. 그래서:

- `test-engine.js` 안에 `runTest(설정값)`이라는 함수 하나를 만들어서, "검사를 진행하는 방법"을 딱 한 번만 만들어뒀습니다.
- 각 검사 파일(`loneliness.html` 등)은 이 함수를 불러와서, **자신만의 문항/점수 기준을 "설정값(config)" 형태로 넘겨주기만** 합니다.

이걸 요리에 비유하면:
- `test-engine.js` = "요리 방법(레시피 틀)" — 재료를 씻고, 썰고, 익히고, 담아내는 **과정** 자체
- 각 `tests/xxx.html` = "오늘 쓸 재료 목록" — 당근, 감자 대신 오늘은 이 재료(문항, 점수 기준)를 쓰겠다는 지정

즉, **새로운 검사를 하나 더 추가하고 싶으면 레시피(엔진)를 다시 짤 필요 없이, 재료 목록(config)만 새로 적으면 됩니다.** 이게 이 프로젝트의 가장 중요한 설계 결정입니다.

### config(설정값) 안에 무엇이 들어있나

```js
const TEST_CONFIG = {
  id: 'mood',                      // 검사를 구분하는 이름표
  intro: { title: '...', hook: '...' },  // 소개 화면에 보일 문구
  questions: [                     // 문항 목록
    { text: '기분이 가라앉았다', options: [
        { label: '전혀 그렇지 않다', score: 0 },
        { label: '가끔 그렇다', score: 1 },
        // ...
    ]}
  ],
  bands: [                         // 총점 구간별 결과 문구
    { max: 7, label: '마음날씨가 맑아요', desc: '...' },
    { max: 15, label: '조금 흐려요', desc: '...' }
  ]
};
runTest(TEST_CONFIG); // ← 엔진에게 "이 설정값으로 검사를 진행해줘"라고 넘김
```

이렇게 문항(questions)과 점수 구간(bands)만 바뀌고, 화면을 그리고 채점하고 결과를 보여주는 로직은 `test-engine.js` 안에 딱 한 번만 존재합니다.

## 5. 단계별 제작 순서

### 1단계 — 첫 화면(허브) 만들기

1. `index.html` 파일 하나를 만들고, 안에 검사 4개를 소개하는 카드(제목, 그림, 짧은 설명)를 HTML로 나열합니다. 각 카드는 `<a href="tests/mood.html">`처럼 눌렀을 때 해당 검사 페이지로 이동하는 **링크**입니다.
2. `hub-core.js`를 만들어 페이지들이 공통으로 쓸 기능을 담습니다. 처음엔 딱 2가지만:
   - **유입경로 기록**: 사용자가 `?src=인스타`처럼 주소 뒤에 붙은 꼬리표를 갖고 들어오면, 이걸 **localStorage**(브라우저에 정보를 저장해두는 공간, 사용자가 페이지를 이동해도 안 지워짐)에 저장해서 "이 사람이 어디서 왔는지"를 계속 기억합니다.
   - **이벤트 기록 함수**: `Hub.log('test_start', 'mood')`처럼 부르면 "누가 mood 검사를 시작했다"는 기록을 Supabase로 보냅니다.
3. `hub.css`를 만들어 전체 디자인의 기준이 되는 **CSS 변수**를 정의합니다.
   - CSS 변수란: `--primary: #FF6B9D;`처럼 색상에 이름을 붙여두고, 이후 모든 스타일에서 `color: var(--primary)`처럼 이름으로 불러 쓰는 방식입니다. 나중에 전체 테마 색을 바꾸고 싶으면 이 한 줄만 고치면 모든 페이지에 적용됩니다.

### 2단계 — 검사 공용 엔진 만들기 (제일 중요하고 어려운 단계)

`test-engine.js`의 `runTest(config)` 함수를 만듭니다. 화면이 3가지 상태 중 하나라는 걸 표현하기 위해 **상태 머신(state machine)** 방식을 씁니다. 상태 머신이란 "지금이 어떤 상태(단계)인지"를 변수 하나로 표현하고, 그 값에 따라 다른 화면을 그리는 방식입니다.

```js
step === -1        → 소개 화면을 그림
0 <= step < 문항수  → 그 번호의 문항 화면을 그림
step === 문항수     → 결과 화면을 그림
```

버튼을 누를 때마다 `step` 값을 바꾸고 `render()`(화면을 다시 그리는 함수)를 호출하는 식으로 화면이 바뀝니다.

**엔진에 실제로 들어가야 하는 기능들 — 실제로 이 순서로 하나씩 만들어졌습니다:**

1. **기본 화면 그리기**: `renderIntro()`, `renderQuestion()`, `renderResult()` 세 함수. 각각 `app.innerHTML = "..."` 형태로 HTML 문자열을 만들어 화면에 끼워 넣습니다.
2. **채점**: 검사 방식이 두 가지입니다.
   - **점수형(score mode)**: 외로움/마음날씨/스트레스처럼, 각 답변의 `score`(점수)를 다 더해서 총점을 구하고, `bands`(구간표) 중 그 점수가 속하는 구간을 찾아 결과로 보여줍니다.
   - **유형형(type mode)**: 연애스타일처럼, 답변마다 `type`(A/B/C/D 같은 유형 이름표)이 있고, 가장 많이 선택된 유형을 결과로 보여줍니다. (이런 걸 "가장 많이 나온 값을 세는" 집계라고 합니다.)
3. **하위영역 분석**: 문항마다 `dim`(어느 영역에 속하는지 이름표, 예: "기분" vs "에너지")을 붙여두면, 결과 화면에서 영역별로 점수를 따로 계산해 막대그래프로 보여줄 수 있습니다.
4. **문항 순서 섞기**: 매번 같은 순서로 문항이 나오면 "항상 3번만 누르면 되네" 하는 패턴이 생길 수 있어서, `shuffleArray()`라는 함수로 문항 순서와 각 문항의 보기 순서를 매번 무작위로 섞습니다. (섞어도 각 보기에 담긴 점수/유형 값은 그대로 붙어 다니기 때문에 채점 결과에는 영향이 없습니다.)
5. **이전 문항으로 돌아가기**: "이전 문항" 버튼을 누르면 `step`을 하나 줄이고 다시 그 문항을 그리는데, 이때 이미 저장해둔 답이 있으면 그 버튼에 "선택됨" 표시를 미리 해둡니다.
6. **결과 공유 기능**:
   - **이미지로 공유**: Canvas API로 결과 카드와 똑같은 디자인의 이미지를 직접 그려서 파일로 만들고, `navigator.share()`(Web Share API — 스마트폰 공유창을 띄우는 브라우저 기능)로 전달합니다.
   - **링크로 공유**: 결과를 `주소?shared=1&score=17`처럼 주소 뒤에 붙여서, 이 링크를 받은 사람이 열면 검사를 다시 안 풀어도 그 결과 화면이 바로 보이게 만듭니다. (`URLSearchParams`라는 JS 기능으로 주소에 붙은 꼬리표를 읽어옵니다.)
   - 스마트폰 공유 기능이 없는 환경(PC 등)에서는 이미지는 자동 다운로드되고, 링크는 클립보드(복사-붙여넣기 임시 저장 공간)에 자동으로 복사됩니다.
7. **유형 결과에서 "잘 맞는 유형 보기"**: 연애스타일처럼 유형형 검사는 각 유형마다 "잘 맞는 유형"이 미리 지정되어 있는데, 이걸 누르면 그 유형의 설명이 아코디언(눌렀다 펴지는 박스)으로 펼쳐지고, "이 유형 결과 전체 보기" 링크를 누르면 6번에서 만든 "링크 공유" 방식을 그대로 재사용해서 그 유형의 결과 화면을 새 탭으로 보여줍니다.
8. **상담 안내 붙이기**: 결과 화면 맨 아래에 `Hub.renderCTA()`(CTA = Call To Action, "다음 행동을 유도하는 버튼")를 호출해서 카카오톡 상담/전화/청소년전화 1388 안내를 붙입니다.

### 3단계 — 검사별 내용(config) 작성하기

엔진이 완성되면, 나머지 검사 파일은 정말 "문항과 기준만 적어놓은 데이터"가 됩니다.

```html
<script src="../js/hub-core.js"></script>
<script src="../js/test-engine.js"></script>
<script>
const TEST_CONFIG = { /* 문항, 점수구간 등 */ };
runTest(TEST_CONFIG);
</script>
```

문항 문구를 만들 때 실제 심리검사 척도(PHQ-9 등, 전문가들이 쓰는 표준화된 설문지)의 "개념"만 참고하고 원문 그대로 베끼지 않도록 하고, 화면 안에 "이건 정식 진단이 아닌 참고용 자가 점검"이라는 안내 문구를 꼭 넣습니다.

### 4단계 — 타로카드 (검사와 다른 별도 코너)

타로는 검사들과 화면 흐름이 아예 달라서 (문항에 답하는 게 아니라 카드를 직접 골라야 함) `test-engine.js`를 같이 쓰지 않고 독립된 폴더로 따로 만들었습니다.
- `tarot-data.js`: 타로카드 78장의 이름과 의미만 담아둔 순수 데이터 파일
- `main.js`: "고민 입력 → 카드 3장 선택 → 결과 보기" 3단계 흐름을 담당

카드를 고르는 화면 UI는 한 번에 완성되지 않고 여러 번 바뀌었습니다:
1. 처음엔 카드를 부채처럼 겹쳐서 화려하게 배치 → 실제로 써보니 카드가 좁게 겹쳐 있어서 원하는 카드를 정확히 누르기 어려움
2. 겹치지 않게 동그란 모양으로 격자 배치 → 누르긴 쉬워졌지만 "카드처럼 안 보인다"는 피드백
3. 최종적으로 카드 뒷면처럼 생긴 세로형 모양(가로세로 비율 2:3, 모서리를 둥글게)으로, 겹치지 않는 격자로 배치

이처럼 **화면(UI)은 처음부터 정답을 알 수 없고, 실제로 브라우저에서 눌러보면서 문제를 발견하고 고쳐나가는 과정을 여러 번 거치는 것이 정상**입니다.

### 5단계 — Supabase 연동 (통계 저장하기)

1. [supabase.com](https://supabase.com)에서 무료 프로젝트를 하나 만듭니다. Supabase는 "데이터베이스(정보를 표 형태로 저장하는 곳)를 클릭 몇 번으로 만들어주고, API로 데이터를 넣고 뺄 수 있게 해주는 서비스"입니다.
2. `supabase_setup.sql`(SQL = 데이터베이스에 표를 만들거나 데이터를 다루는 명령어 언어) 코드를 Supabase에 실행해서 `hub_events`라는 표(테이블)를 만듭니다. 이 표에는 "누가, 언제, 어떤 검사를, 어떤 행동을 했는지" 한 줄씩 쌓입니다.
3. `hub-core.js`의 `Hub.log()` 함수가 주요 순간마다(검사 시작, 검사 완료, 상담 버튼 클릭 등) `fetch()`(JS에서 인터넷으로 데이터를 보내고 받는 기본 기능)로 이 표에 기록을 추가합니다.
4. `stats.html`에서 같은 방식으로 표에 쌓인 데이터를 읽어와서 숫자로 보여줍니다 (오늘 몇 명이 검사했는지 등).
5. **보안 설정**: Supabase에는 **RLS(Row Level Security, 행 단위 보안)** 라는 기능이 있어서, "누구나 쓰기는 가능하지만 읽기는 못 하게" 같은 세밀한 권한 설정이 가능합니다. 민감한 정보(예: 회원 개인정보)가 담긴 표는 **RPC(Remote Procedure Call — 미리 정해둔 함수만 실행하게 허용하고, 표 전체를 직접 열람은 못 하게 막는 방식)**로만 접근 가능하게 잠가두는 것이 안전합니다.

### 6단계 — 배포하기 (인터넷에 실제로 올리기)

1. GitHub(github.com)에 계정을 만들고 새 저장소(repository)를 만듭니다.
2. 컴퓨터에 있는 프로젝트 폴더를 그 저장소와 연결하고, `git add`(변경된 파일을 "저장할 목록"에 추가) → `git commit`(그 목록을 하나의 저장 지점으로 남김) → `git push`(GitHub에 업로드)로 파일을 올립니다.
3. 저장소 맨 위 폴더에 `.nojekyll`이라는 빈 파일을 하나 추가합니다. (GitHub Pages는 기본적으로 Jekyll이라는 변환 도구를 거치는데, 이게 `_`로 시작하는 파일/폴더를 무시해버릴 수 있어서, 이 파일을 두면 그 과정을 건너뛰고 파일을 있는 그대로 보여줍니다.)
4. GitHub 저장소의 Settings(설정) → Pages 메뉴에서 "main 브랜치에서 배포"로 지정하면, 몇 분 뒤 `https://내계정.github.io/저장소이름/` 주소로 실제 인터넷에 사이트가 공개됩니다.
5. 이후 수정할 때마다: 파일 수정 → `git add/commit/push` 반복 → 자동으로 몇 분 내에 실제 사이트에 반영됩니다. 브라우저가 예전 파일을 기억(캐시)하고 안 바꿔주는 경우를 막기 위해, `<link>`나 `<script>` 주소 끝에 `?v=7`처럼 버전 번호를 붙여두고 수정할 때마다 숫자를 올려줍니다.

## 6. AI를 활용해서 만드는 방법

사실 이 프로젝트도 위 과정을 사람이 한 줄 한 줄 직접 코딩한 게 아니라, **Claude 같은 AI 코딩 도구와 대화하면서** 만들어졌습니다. 코딩을 전혀 몰라도 이 방식으로 실제 서비스를 만들 수 있습니다. 어떻게 하는지 정리합니다.

### 6-1. 어떤 도구를 쓰나

- **Claude Code / Cursor / GitHub Copilot** 같은 "AI 코딩 도구": 채팅하듯 "이런 기능을 만들어줘"라고 말하면, AI가 실제로 파일을 읽고 쓰고 코드를 작성/수정해주는 프로그램입니다. 이 문서를 쓰고 있는 지금 이 대화도 그런 도구(Claude Code) 위에서 진행되고 있습니다.
- 이런 도구는 단순히 코드 텍스트만 뱉어주는 게 아니라, **직접 파일을 만들고(Write), 기존 파일을 수정하고(Edit), 명령어를 실행하고(Bash), 브라우저를 열어서 실제로 클릭해보고 확인(Browser)까지** 할 수 있습니다.

### 6-2. 실제로 어떤 순서로 대화하며 만들었나 (이 프로젝트의 실제 진행 과정)

1. **큰 그림부터 요청**: "청소년 대상 심리 자가진단 웹앱을 만들고 싶어" 처럼 전체 목적을 먼저 설명 → AI가 구조(허브 페이지 + 검사 엔진 + 개별 검사)를 제안하고 뼈대 코드를 작성
2. **기능을 하나씩, 구체적으로 요청**: 한 번에 모든 걸 요청하지 않고, "문항 순서를 섞어줘", "이전 문항으로 돌아갈 수 있게 해줘", "결과에서 나랑 맞는 유형도 볼 수 있게 해줘"처럼 **한 번에 하나의 기능**을 요청. 요청이 구체적일수록 AI가 정확하게 만듭니다.
3. **AI가 만든 결과를 실제로 확인**: AI가 코드만 고치고 끝내는 게 아니라, 직접 브라우저를 띄워서 버튼을 눌러보고, 스크린샷을 찍어보고, "만점이 정확히 나오는지" 같은 걸 검증한 뒤에 "됐다"고 보고합니다. 사람은 그 결과를 보고 마음에 안 들면 바로 피드백을 줍니다.
4. **마음에 안 들면 바로 되돌리거나 다시 요청**: 예를 들어 타로 카드 UI를 "동그랗게" 바꿨더니 "카드처럼 안 보인다"고 피드백을 주니 AI가 다시 카드 모양으로 수정한 것처럼, **한 번에 완벽한 결과를 기대하지 않고 보면서 계속 다듬어가는 대화**가 핵심입니다.
5. **완성되면 배포까지 AI에게 맡김**: "배포해줘"라고 하면 AI가 `git add/commit/push` 명령어까지 실행해서 실제 인터넷 주소에 반영합니다.

### 6-3. AI에게 잘 요청하는 방법 (프롬프트 팁)

- **무엇을, 왜 원하는지 같이 말하기**: "버튼을 크게 해줘"보다 "이전 문항 버튼이 잘 안 보여서 크게 만들어줘"처럼 이유를 같이 말하면 AI가 더 적절한 방법을 고릅니다.
- **한 번에 하나씩**: 여러 기능을 한 문장에 다 넣기보다, 기능 단위로 나눠서 요청하면 결과를 확인하기도 쉽고 문제가 생겼을 때 원인을 찾기도 쉽습니다.
- **실제로 써보고 피드백 주기**: AI가 "완료했다"고 해도 직접 링크를 눌러보고 이상하면 바로 말하기 (예: "링크가 3개나 가는데 하나만 가면 좋겠어" 처럼 실제 사용 경험을 전달하는 게 코드 용어로 설명하는 것보다 훨씬 효과적)
- **모르는 용어는 그냥 모른다고 말하기**: "완전 기초야, 용어 설명도 넣어줘"처럼 요청하면 AI가 눈높이를 맞춰서 설명합니다. 굳이 개발 용어를 써가며 요청할 필요가 없습니다.
- **기존 걸 참고해서 만들라고 하기**: 새 검사를 추가하고 싶으면 "love.html처럼 만들어줘"처럼 이미 있는 것을 예시로 들면 AI가 같은 패턴(공용 엔진 재사용)을 따라서 일관성 있게 만듭니다.

### 6-4. AI로 만들 때도 사람이 꼭 챙겨야 하는 것

- **실제로 눌러보고 확인하기**: AI가 "확인했다"고 말해도, 결과물이 배포된 실제 주소를 사람이 한 번은 직접 열어보는 게 안전합니다.
- **민감한 작업은 승인하기**: 파일을 지우거나, 외부에 데이터를 보내거나, 비밀번호/API 키 같은 걸 다루는 작업은 AI가 먼저 "이렇게 해도 될까요?"라고 물어보게 하고, 사람이 직접 확인 후 진행하는 게 안전합니다. (이 프로젝트에서는 회원 정보 같은 민감한 데이터는 RPC로 잠가두고, 통계처럼 민감하지 않은 데이터만 공개하는 식으로 AI와 함께 보안 정책을 정했습니다.)
- **왜 이렇게 만들었는지 한 번씩 물어보기**: "왜 이 구조로 만들었어?"처럼 물어보면 AI가 이유를 설명해주기 때문에, 코딩을 몰라도 전체 그림을 이해하는 데 도움이 됩니다. (이 문서 자체도 그런 질문에서 시작되었습니다.)

## 7. 수정한 코드가 잘 동작하는지 확인하는 방법

코드를 고칠 때마다 눈으로 직접 확인하는 습관이 중요합니다.

1. 컴퓨터 안에서 프로젝트 폴더 위치에 "정적 파일 서버"(파일을 웹페이지처럼 브라우저에서 열어볼 수 있게 해주는 간단한 프로그램)를 실행합니다. 예: `python -m http.server 8080` 명령어를 실행하면 `http://localhost:8080`이라는 주소로 내 컴퓨터 안에서만 볼 수 있는 임시 웹사이트가 뜹니다. (`localhost`는 "내 컴퓨터 자신"을 가리키는 주소입니다.)
2. 브라우저로 그 주소에 접속해서, 실제 사용자처럼 버튼을 눌러보며 시나리오를 재현합니다. 예: 문항 전부에 "항상 그렇다"만 선택했을 때 정확히 만점이 나오는지, 이전 문항 버튼으로 답을 바꿨을 때 최종 점수에 잘 반영되는지 등.
3. 화면 폭이 좁은 스마트폰 화면에서도 레이아웃이 깨지지 않는지 확인합니다.
4. 브라우저의 "개발자 도구"(F12 등으로 열 수 있는, 에러 메시지를 보여주는 창)에서 빨간 에러 메시지가 없는지 확인합니다.

## 8. 이 구조 덕분에 새 기능을 쉽게 추가할 수 있는 이유

- **검사를 하나 더 추가하고 싶다** → `tests/새검사.html` 파일 하나만 새로 만들고 config만 작성. 엔진(`test-engine.js`)은 건드릴 필요 없음.
- **모든 검사에 공통으로 적용될 기능을 추가하고 싶다** (예: "이전 문항 버튼", "공유할 때 링크가 중복되던 문제 수정") → `test-engine.js` 딱 한 곳만 고치면 4개 검사 전부에 동시 반영됨.
- **디자인 톤을 바꾸고 싶다** (색상, 여백, 둥근 정도) → `hub.css`의 CSS 변수 값만 바꾸면 전체 페이지에 일괄 적용됨.

이게 바로 "공용 엔진 + 설정값(config) 분리"라는 구조를 처음부터 잡아둔 이유입니다. 로직이 한 곳에만 있으면, 고칠 때도 한 곳만 고치면 되고, 실수할 확률도 줄어듭니다.

### 더 깊이 알고 싶다면 어떤 순서로 공부하면 좋을까

1. HTML/CSS 기초 (화면에 글자와 버튼을 배치하고 꾸미는 법)
2. JavaScript 기초 (변수, 함수, 조건문, 배열, 객체 — 이 문서 0장에서 설명한 용어들)
3. DOM 조작 (`document.querySelector`, `addEventListener` 등으로 JS가 화면을 바꾸는 법)
4. `fetch`로 API 호출하는 법, JSON 다루는 법
5. Git/GitHub 기본 명령어 (`git add`, `commit`, `push`, `pull`)
6. 이 저장소의 `js/test-engine.js` 파일을 위에서부터 한 줄씩 읽어보기 — 지금까지 설명한 개념들이 실제 코드로 어떻게 쓰였는지 확인하는 것이 가장 빠른 학습법입니다.

다만 위 순서를 다 공부한 뒤에 시작해야 하는 건 아닙니다. 6장에서 설명한 것처럼 **AI 코딩 도구와 대화하면서 바로 만들어보고, 만들어진 코드를 읽으면서 위 개념들을 하나씩 확인해나가는 것**도 충분히 좋은 방법입니다.
